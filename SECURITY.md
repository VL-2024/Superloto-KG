# X2 LOTO — требования безопасности для браузерных игр

Этот документ задаёт обязательные требования для production-версий моментальных игр X2 LOTO. Он применяется ко всем браузерным играм независимо от конкретной механики.

## 1. Основной принцип

Frontend игры считается недоверенной средой.

Пользователь технически может:

- скачать HTML/JS/CSS и ассеты;
- изменить JavaScript локально;
- подменить URL-параметры;
- повторить сетевой запрос;
- вызвать API напрямую вне интерфейса игры;
- отправить поддельные `postMessage` события;
- попытаться встроить игру на другом сайте.

Поэтому ни одна денежная операция и ни один финансовый результат не должны зависеть от данных, вычисленных только в браузере.

**LMS является единственным источником истины для покупки билета, сценария, выигрыша и баланса.**

---

## 2. Что разрешено хранить во frontend

Во frontend допустимы:

- интерфейс;
- анимации;
- графические ассеты;
- локализация;
- визуальная физика;
- преобразование полученного от LMS `scenario` в конкретную анимацию;
- не денежная demo-логика в отдельной demo-сборке.

Во frontend production-версии не должны находиться:

- секретные ключи;
- пароли;
- API secrets;
- приватные сертификаты;
- алгоритм определения реального выигрыша;
- полный пул реальных билетов;
- информация об оставшихся выигрышных билетах серии;
- серверный RNG;
- возможность самостоятельно назначить `scenario`, `win` или `balance` в REAL-режиме.

---

## 3. Запуск игры из LMS

Production-игра должна запускаться только из авторизованной LMS-сессии.

Рекомендуемая схема:

1. Игрок авторизован в X2 LMS.
2. LMS создаёт короткоживущий `launchToken` для конкретной игры.
3. LMS открывает игру в iframe или отдельном окне.
4. LMS передаёт `X2_LMS_INIT` и/или токен запуска.
5. Игра использует этот контекст только для обращения к LMS.

### Требования к launchToken

Токен должен:

- создаваться только сервером LMS;
- иметь короткий срок действия, рекомендуемо 2–10 минут;
- быть привязан к конкретному пользователю/сессии;
- быть привязан к конкретному `gameId`;
- содержать или серверно связываться с разрешённым режимом `real/demo`;
- иметь уникальный `nonce` или иной идентификатор против повторного использования;
- проверяться сервером при денежных операциях;
- не содержать лишние персональные данные в открытом виде.

Допустимые реализации: подписанный JWT либо непрозрачный случайный token, состояние которого хранится на сервере.

**Секрет подписи токена никогда не передаётся frontend.**

---

## 4. PayTicket

Запрос типа:

```http
GET /api/Lotto.Users.cls?Method=PayTicket&gameId=137&amount=100
```

не должен быть достаточен сам по себе для покупки билета.

LMS при каждом `PayTicket` обязана серверно проверить:

- авторизован ли игрок;
- действительна ли его сессия;
- действителен ли launchToken/игровой контекст;
- разрешена ли данному пользователю эта игра;
- совпадает ли `gameId` с разрешённым для запуска;
- разрешён ли выбранный `amount` для этой игры;
- находится ли пользователь в REAL-режиме;
- достаточно ли средств;
- не был ли этот запрос уже обработан.

Параметры `gameId` и `amount`, пришедшие из браузера, считаются пользовательским вводом и должны валидироваться на сервере.

---

## 5. Защита от двойного списания

Покупка билета должна быть идемпотентной.

Для каждого запуска покупки рекомендуется использовать уникальный `requestId` / `idempotencyKey`.

При повторе одного и того же запроса из-за:

- двойного клика;
- повторной отправки браузером;
- сетевого таймаута;
- ручного replay;

LMS должна вернуть результат уже созданного билета, а не списывать деньги повторно.

Одна операция покупки = один `ticketId`.

---

## 6. Финансовый результат

Игра не имеет права определять реальный денежный результат.

LMS возвращает авторитетный ответ, например:

```json
{
  "ticketId": "123456789",
  "scenario": 7,
  "win": 1000,
  "balance": 5420
}
```

Frontend может использовать `scenario` только для визуализации.

Поля, присланные frontend обратно на сервер, такие как:

- `win`;
- `multiplier`;
- `scenario`;
- `balance`;

не должны приниматься сервером как доказательство денежного результата.

Авторитетны только данные, сформированные LMS/серверной игровой логикой.

---

## 7. Баланс

Frontend не должен самостоятельно вычислять реальный баланс по формуле:

`старый баланс - ставка + выигрыш`.

После денежной операции игра показывает `balance`, полученный от LMS.

Это исключает расхождения при бонусах, налогах, блокировках, параллельных операциях и иных серверных корректировках.

---

## 8. REAL и DEMO

REAL и DEMO должны быть логически разделены.

### REAL

- всегда обращается к LMS;
- требует авторизованную сессию;
- требует серверную проверку режима;
- денежный результат приходит только с сервера.

### DEMO

- не вызывает реальный `PayTicket`;
- не списывает реальные средства;
- использует только виртуальный баланс;
- не должен иметь возможность переключить серверную операцию в REAL простой подменой URL.

Для production рекомендуется удалить `mock`-логику из REAL-сборки либо гарантированно собирать её с `mock=false` без возможности включения пользователем через query string.

---

## 9. URL-параметры

Любые URL-параметры считаются недоверенными.

Например:

- `gameId`;
- `denomination`;
- `mode`;
- `scenario`;
- `balance`;
- `mock`.

В production они не могут сами по себе разрешать денежную операцию или менять финансовый результат.

Особенно важно: параметры `scenario`, `win`, `balance`, `mock=true` должны использоваться только в dev/demo окружении и не влиять на REAL.

---

## 10. postMessage / iframe

Если игра работает внутри iframe, необходимо проверять origin сообщений.

В production нельзя оставлять:

```js
allowedParentOrigins: ['*']
```

или без необходимости отправлять чувствительные события через:

```js
postMessage(data, '*')
```

Должен использоваться точный список production-origin, например домен LMS X2.

При получении `postMessage` необходимо проверять:

- `event.origin`;
- ожидаемый `type`;
- типы и диапазоны полей сообщения.

Для самой страницы игры рекомендуется ограничить встраивание через CSP `frame-ancestors` только разрешёнными доменами X2.

---

## 11. CORS, cookies и CSRF

API LMS должен разрешать запросы только с необходимых production-origin.

Не использовать `Access-Control-Allow-Origin: *` для авторизованных денежных запросов.

Если используется cookie-сессия:

- `Secure`;
- `HttpOnly` для session cookie;
- корректный `SameSite`;
- защита от CSRF там, где это требуется архитектурой.

Проверка `Origin`/`Referer` полезна как дополнительная мера, но не заменяет серверную авторизацию.

---

## 12. TLS

Все production-запросы игры и LMS выполняются только по HTTPS.

HTTP для REAL-режима не допускается.

---

## 13. Ограничение частоты запросов

LMS должна применять rate limiting минимум к:

- запуску игровой сессии;
- `PayTicket`;
- запросам баланса;
- операциям пополнения.

Лимиты должны учитывать пользователя, сессию и при необходимости IP/device fingerprint как вспомогательные признаки.

Rate limiting не должен заменять авторизацию.

---

## 14. Логи и аудит

Для каждой покупки желательно хранить серверный аудит:

- timestamp;
- внутренний playerId;
- sessionId или его безопасный идентификатор;
- `gameId`;
- `requestId/idempotencyKey`;
- `ticketId`;
- `amount`;
- `scenario`;
- `win`;
- balance before/after;
- результат операции;
- технический код ошибки при отказе.

В логах запрещено сохранять целиком:

- session cookies;
- launchToken;
- API secrets;
- пароли.

При необходимости сохраняется только хэш/последние символы идентификатора токена.

---

## 15. Production build

Публично размещаемая production-сборка должна содержать только то, что необходимо браузеру.

Рекомендуется:

- private GitHub repository для исходников;
- CI/CD сборка;
- minify JS/CSS;
- при необходимости obfuscation как дополнительная, а не основная защита;
- не публиковать production source maps;
- не включать тестовые файлы, dev-конфиги и секреты;
- удалить неиспользуемые demo/debug endpoints.

Важно: minification/obfuscation не защищает финансовую механику. Главная защита — серверная архитектура.

---

## 16. Ассеты и интеллектуальная собственность

Графику, интерфейс и клиентский код технически возможно скачать из браузера.

Поэтому:

- исходники рекомендуется хранить в private repositories;
- production должен содержать copyright/licence notice X2;
- оригинальные мастер-ассеты не публикуются, если браузеру достаточно оптимизированных копий;
- серверная часть должна делать скопированный frontend бесполезным без X2 LMS.

---

## 17. Критические запреты

В production запрещено:

1. Доверять `scenario`, `win`, `balance` или `multiplier`, рассчитанным браузером.
2. Разрешать `PayTicket` без авторизованного игрового контекста.
3. Хранить секреты в `config.js`, HTML или JavaScript.
4. Оставлять возможность включить REAL через простой URL-параметр.
5. Оставлять рабочий `mock=true` в REAL-сборке.
6. Использовать `allowedParentOrigins: ['*']` для production-интеграции.
7. Допускать повторный запрос покупки с повторным списанием средств.
8. Публиковать алгоритм реального распределения оставшихся билетов, если он используется сервером для выдачи результатов.

---

## 18. Целевая схема X2

```text
Игрок
  ↓
X2 LMS (авторизация)
  ↓ создаёт short-lived launchToken
Игра в браузере
  ↓ PayTicket + авторизованный контекст + requestId
X2 LMS / серверная игровая логика
  ↓
создание ticketId → определение scenario/win → списание/начисление → новый balance
  ↓
Игра получает только готовый результат
  ↓
визуализирует scenario
```

Даже если frontend игры будет полностью скопирован, без действующей X2 LMS-сессии и серверного игрового контекста он не должен позволять купить настоящий билет или получить действительный денежный результат.

---

## 19. Checklist перед выпуском каждой игры

- [ ] Исходный репозиторий переведён в private или production не зависит от публичного dev-репозитория.
- [ ] REAL использует только LMS `PayTicket`.
- [ ] `mock` невозможно включить в REAL через URL.
- [ ] Нет секретов во frontend.
- [ ] `gameId` и `amount` серверно валидируются.
- [ ] Есть авторизация пользователя.
- [ ] Есть короткоживущий игровой контекст / launchToken.
- [ ] Есть защита от replay и двойного списания.
- [ ] Реальный баланс берётся только из LMS.
- [ ] `scenario/win` формирует только сервер.
- [ ] `postMessage` ограничен разрешёнными origin.
- [ ] CORS не открыт на `*` для денежных запросов.
- [ ] Production работает только через HTTPS.
- [ ] Включён audit logging.
- [ ] Source maps и dev/debug файлы не опубликованы.
- [ ] Проверено, что скачанная копия frontend не может выполнять реальные операции без LMS.
